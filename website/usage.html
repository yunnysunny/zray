01

先确认你能不能用Is this for you?

zray 是一个客户端，服务端不需要它。要跑起来需要三样东西： zray is a client; nothing is deployed on the server side. You need three things:

需要Need 说明Notes
一台 Linux 机器A Linux box 代理服务只在 Linux 上运行。路由器（OpenWrt / ImmortalWrt）、软路由、树莓派、VPS 都行。macOS / Windows 上只能编译和跑 probe。The proxy service runs on Linux only: a router (OpenWrt / ImmortalWrt), a small x86 or ARM mini-PC, a Raspberry Pi, a VPS. On macOS / Windows you can build it and run probe, nothing else.
一个服务端节点A node to connect to REALITY（VLESS + xtls-rprx-vision），或者普通 VLESS + TLS（机场常见的那种）。协议必须是 VLESS，Trojan / VMess / Shadowsocks 都不支持。REALITY (VLESS + xtls-rprx-vision), or plain VLESS + TLS (what most commercial providers offer). VLESS only — Trojan / VMess / Shadowsocks are not supported.
系统的出口方式A way to route traffic in 你的手机、电脑、整栋房子要么手动填 SOCKS5，要么靠透明代理自动接管。Either you point clients at its SOCKS5 port by hand, or a transparent nft rule hands it the traffic.

如果你只有一台线路好、IP 也干净的服务器，直连就够了，不需要链式那一套。见链式出站教程开头的判断。 If you have one server with both a good route and a clean IP, use it directly; the chaining machinery buys you nothing. See the decision section at the top of the chaining tutorial.

它不是什么：不是图形客户端，没有订阅、没有自动测速、没有负载均衡、没有日志级别开关（每条连接的生命周期都打到 stderr）。这些不在设计目标里。 What it is not: not a GUI client, no subscriptions, no automatic latency testing, no load balancing, no log level switch (every connection logs its lifecycle to stderr). Those are outside the design goals.

02

五分钟跑起来（SOCKS5 模式）Running in five minutes (SOCKS5)

选对二进制Pick the right binary

每个 tag 的 Release 里都有五个静态 musl 二进制，没有动态依赖，也不用装任何库： Every tagged release carries five static musl binaries. No shared libraries, nothing to install:

文件File 适用设备Target
zray-mipsel-softfloat小端 MIPS，绝大多数 MT7621 / MT7620 路由器（小米 AC2100、红米 AC2100、新路由 3 等）Little-endian MIPS — most MT7621 / MT7620 routers (Xiaomi AC2100, Redmi AC2100, Newifi 3, ...)
zray-mips-softfloat大端 MIPS，少数老设备Big-endian MIPS, a few older boxes
zray-arm-v7ARMv7，如多数高通 / 博通 A7 路由器、树莓派 2/3ARMv7: most Qualcomm / Broadcom A7 routers, Raspberry Pi 2/3
zray-aarch64ARM64，如树莓派 4、ARM 软路由、ARM VPSARM64: Raspberry Pi 4, ARM mini-PCs, ARM VPS
zray-x86_64普通 PC / x86 软路由 / x86 VPSAny PC / x86 mini-PC / x86 VPS

uname -m 在 MIPS 上只回 mips，分不出大小端。在 OpenWrt 上用发行版架构串最准： uname -m prints mips for both MIPS endiannesses, so it cannot tell you which one you have. On OpenWrt ask the distro instead:

OpenWrt · DISTRIB_ARCH 
. /etc/openwrt_release && echo $DISTRIB_ARCH
# mipsel_24kc / mips_24kc / aarch64_generic / arm_cortex-a7_neon-vfpv4 / x86_64

mipsel 开头 → zray-mipsel-softfloat，mips_ 开头 → zray-mips-softfloat，其余按上表对。还拿不准就再跑一次 opkg print-architecture，mipsel_ 前缀即小端。 mipsel* → zray-mipsel-softfloat, mips_* → zray-mips-softfloat, everything else maps by the table. opkg print-architecture prints the same string.

下载、校验、放到固定位置Download, verify, put it somewhere permanent

/mnt/zray 
mkdir -p /mnt/zray
cd /mnt/zray
wget -O zray https://github.com/yunnysunny/zray/releases/latest/download/zray-mipsel-softfloat
wget -O zray.sha256 https://github.com/yunnysunny/zray/releases/latest/download/zray-mipsel-softfloat.sha256
chmod 755 zray
sha256sum zray      # 和 zray.sha256 里的第一列目视比对 / compare with the first column
./zray              # 没有配置文件时报 cannot read config.json，说明二进制能跑

除了一个配置文件路径之外，zray 不接受任何参数：没有 -h、没有 --version，zray --help 会被当成文件名去读。版本号看启动日志第一行。不要放在 /tmp（重启就没了）；/mnt/zray 这类数据分区在 OpenWrt 上重启后仍在。 Apart from a config path, zray takes no arguments: no -h, no --version. zray --help is treated as a file name. The version is the first field of the first startup log line. Do not leave it in /tmp (wiped on reboot); /mnt/zray on OpenWrt survives reboots.

写一份最小配置Write a minimal config

config.json · REALITY 
{
  "listen": "127.0.0.1:1080",
  "server": "服务器地址 / host or IP",
  "port": 443,
  "sni": "伪装域名 / camouflage site",
  "security": "reality",
  "public_key": "服务端 publicKey / server publicKey",
  "short_id": "服务端 shortId，没有就留空 / empty if none",
  "uuid": "你的 uuid / your uuid",
  "max_connections": 64
}

其余字段都有默认值，见 config.example.json。两条硬性规则： Everything else has a default; see config.example.json. Two hard rules:

  • 配置里出现不认识的键会直接报错退出（bad config: UnknownField）。多写一个逗号、键名拼错，都不会被静默忽略。An unknown key is a startup error (bad config: UnknownField). A trailing comma or a misspelled key is never silently ignored.
  • security 是显式声明的。"reality" 必须给 public_key；"tls" 不许出现 public_key / short_id。写错组合就报错，不会悄悄降级成不校验证书的 TLS。security is explicit. "reality" requires public_key; "tls" rejects public_key / short_id. A wrong combination fails at startup instead of quietly downgrading to unverified TLS.

实用一下的话，把 max_connections 按内存算（每个槽约 93 KiB，见第 6 节）。 Size max_connections from the memory you have (about 93 KiB per slot, see section 06).

前台跑一次，看着日志Run it in the foreground and read the log

启动日志就是自检报告The startup log is the health report

mode reality 就是 REALITY 模式；如果是 mode tls, verify NONE -- WARNING: ...，说明你在连普通 VLESS+TLS 节点，证书不校验，链路上的任何人都有可能冒充它。 mode reality means REALITY. mode tls, verify NONE -- WARNING: ... means you are on a plain VLESS+TLS node with no certificate verification: anyone on the path can impersonate it.

验证真的通了Prove it actually works

curl 
curl --socks5-hostname 127.0.0.1:1080 https://www.cloudflare.com/cdn-cgi/trace
# ip= 应为服务器出口 IP，loc= 是国家地区码
curl --socks5-hostname 127.0.0.1:1080 https://ipinfo.io/json
# 第二条验证 DNS 也走隧道 / the second check proves DNS goes through too

两条都通，这台机器上的 SOCKS5 模式就配好了。前端接上它就行：SwitchyOmega、sing-box 的 socks outbound、手机上任意支持 SOCKS5 的客户端，地址填 路由器IP:1080。 Once both work, point a client at it: SwitchyOmega, a sing-box socks outbound, any phone SOCKS5 client — address router-ip:1080.

不支持 / 需要注意： Not supported / watch out for:

  • type=grpc、type=httpupgrade、type=quic：都没有实现，只能用 tcp 和 ws。type=grpc, type=httpupgrade, type=quic: not implemented. tcp and ws only.
  • ws 的 early data（链接里带 ed=2048 这类参数）：不实现。别把它塞进 ws_path，服务端真发 early data 时连接会以 WsEarlyData 断开。大多数服务端在没有客户端请求时不会主动发。WebSocket early data (ed=2048 and friends): not implemented. Do not put it into ws_path; if the server sends early data alongside the 101, the connection dies with WsEarlyData.

04

三种用法Three ways to deploy

本机 / 局域网 SOCKS5（最简单）Local / LAN SOCKS5 (simplest)

就是第 02 节那套。适合：单台机器或几台设备手动挂代理；先验证节点可用，再折腾透明代理。 What section 02 sets up. Good for one machine or a handful of devices, and for validating a node before touching transparent proxying.

UDP 走 SOCKS5 UDP ASSOCIATE，用 XUDP（VLESS mux）封装。注意两点：只支持带 Vision 的 TCP 节点（ws 节点没有 UDP），载荷超过约 600 字节可能被服务端出口丢弃（DNS 正常，QUIC 一般不通）。分片不支持，现实中也没有客户端用。 UDP rides SOCKS5 UDP ASSOCIATE, wrapped in XUDP (VLESS mux). Two limits: Vision TCP outbounds only (a ws outbound carries no UDP), and payloads above roughly 600 bytes may be dropped by the server's outbound (DNS works, QUIC generally does not). Fragmentation is not supported; no real client uses it.

透明代理（路由器当网关）Transparent proxy (the router is the gateway)

目标：局域网里的设备什么都不用配，命中规则的流量自动进隧道。 Goal: LAN devices need no configuration, matching traffic enters the tunnel by itself.

1. 配置两个入口。listen 留着当调试用，redirect 才是给 nft 喂流量的： 1. Configure two inbounds. Keep listen for debugging; redirect is what nft feeds:

config.json · 两个入口two inbounds 
{
  "listen": "127.0.0.1:10800",
  "redirect": "0.0.0.0:1080",
  "sniff": true,
  "server": "服务器地址 / host or IP",
  "port": 2443,
  "bootstrap_dns": "223.5.5.5",
  "...": "其余同前 / the rest as before"
}

2. nft 规则把命中的 IP 重定向到 redirect 端口。典型的按域名分流：DNS 侧（dnsmasq + chinadns-ng，或 smartdns）把命中 gfwlist 的域名解析出的 IP 写进一个 nft 集合，再由这张表负责转发： 2. Redirect matching destinations to the redirect port. A typical domain-based split: the DNS side (dnsmasq + chinadns-ng, or smartdns) writes the IPs of matched domains into an nft set, and this table forwards them:

nft · inet gfw 
table inet gfw {
    set iplist { type ipv4_addr; flags interval; }
    chain prerouting { type nat hook prerouting priority 0;
        ip daddr @iplist ip protocol tcp redirect to :1080 }
    chain output     { type nat hook output priority filter;
        ip daddr @iplist ip protocol tcp redirect to :1080 }
}

prerouting 管其他设备，output 管路由器自己。redirect 用的是 SO_ORIGINAL_DST，所以端口写的是 zray 的 redirect 端口（上例 1080），不是 listen。 prerouting covers other devices, output covers the router itself. redirect relies on SO_ORIGINAL_DST, so the port here is zray's redirect port (1080 above), never listen.

3. 两条必须避开的坑： 3. Two traps that must be avoided:

  • 服务器自己的 IP 不能进那个集合。否则 zray 连服务器的流量又被自己拦回来，变成死循环（症状：启动正常、一有流量就满槽位、日志里全是失败）。用 ip daddr != <服务器 IP> 排除，或者在 DNS 侧把服务器域名加进直连名单。The server's own IP must never land in that set. Otherwise zray's connection to its server is redirected back into zray — a loop whose symptom is a healthy start, then instant slot exhaustion and a log full of failures. Exclude it with ip daddr != <server IP>, or put the server hostname on the direct list.
  • 解析 server 的解析器不能依赖这条隧道。如果 dnsmasq / chinadns-ng 的 DoT 上游本身走 zray，开机时两边互相等，谁都起不来。这时把 bootstrap_dns 设成公共 DNS（如 223.5.5.5），启动时那次解析就完全不经过本地解析器。Whatever resolves server must not depend on the tunnel. If dnsmasq / chinadns-ng forwards DoT through zray, both wait for each other at boot and neither starts. Set bootstrap_dns to a public resolver (e.g. 223.5.5.5) so the startup lookup bypasses the local resolver entirely.

4. sniff 保持开启。透明代理只拿得到目标 IP，sniff 让它从首包解出 TLS SNI 或 HTTP Host，把目标换成域名。目标 IP 有可能命中 rules 时，zray 最多等 1 秒做这次嗅探——这是那 1 秒的来源，正常。 4. Leave sniff on. A transparent inbound only sees the destination IP; sniff extracts the TLS SNI or HTTP Host from the first client bytes and swaps the IP for the name. When the target IP could match a rules entry, zray waits up to one second for that sniff — that second is expected.

5. 验证：在局域网另一台机器上不配代理，直接： 5. Verify from another LAN machine with no proxy configured:

curl 
curl https://www.cloudflare.com/cdn-cgi/trace      # ip= 应为服务器出口 IP
curl https://www.baidu.com                          # 应正常（不在集合里，直连）

多节点、按域名分流、链式出站Several nodes, domain routing, chaining

需要「线路好的机器」和「IP 干净的机器」各一台时用这个：rules 把少数域名分给一组 exit，其余走 default。 For when "a machine with a good route" and "a machine with a clean IP" are different boxes: rules send a few domains to a group of exits, everything else stays on default.

config.json · outbounds + rules 
{
  "outbounds": [
    { "tag": "relay", "server": "...", "security": "reality", "public_key": "...", "uuid": "..." },
    { "tag": "exit-a", "server": "...", "security": "tls", "tls_verify": "none",
      "uuid": "...", "network": "ws", "ws_path": "/vless-ws", "flow": "none", "dialer": "relay" }
  ],
  "rules": [
    { "domain_suffix": ["openai.com", "chatgpt.com", "claude.ai"], "outbound": ["exit-a"] }
  ],
  "default": ["relay"]
}

规则要点：outbound 是一个组，组内成员之间才做故障切换（fail_backoff_s，默认 30 秒）；命中的规则失败后不会退回 default，这是故意的——宁可打不开，也不让本该走干净 IP 的请求从别处出去。链式的完整原理、封装层次、代价和验证方法都在链式出站教程里。 Rules worth knowing: outbound is a group, and failover (fail_backoff_s, 30 s by default) only rotates inside that group; a matched rule never falls back to default. That is deliberate — better a failed request than a request that was supposed to leave from the clean IP going out somewhere else. The full mechanics live in the chaining tutorial (Chinese).

OpenWrt：用仓库里的 procd 脚本OpenWrt: the procd script in the repo

procd

scp config.json       root@router:/mnt/zray/config.json

06

调优：把有限的 CPU 和内存用对地方Tuning: spend the scarce CPU and RAM well

内存：max_connections × 93 KiBMemory: max_connections × 93 KiB

启动日志最后一段就是账：64 slots x 93 KiB = 5937 KiB。槽位在启动时一次性分配，不随流量增长，超出就拒绝新连接（conn table full）。 The tail of the startup line is the ledger: 64 slots x 93 KiB = 5937 KiB. Slots are allocated once at startup and do not grow with traffic; when they run out, new connections are refused (conn table full).

场景Scenario 估算Estimate
普通 SOCKS5 / 透明代理Plain SOCKS5 / transparent并发连接数 × 93 KiBconcurrent connections × 93 KiB
链式（dialer）Chained (dialer)再乘 2：每条链式连接占两个槽（客户端那条 + hop 那条）× 2: each chained connection holds two slots (client side + hop)
128 MB 内存的路由器（可用约 20 MB）128 MB router (~20 MB free)32–64 个槽比较合适32–64 slots is a sensible range

64 槽 ≈ 5.8 MB，128 槽 ≈ 11.6 MB。先给 64，出现 conn table full 再往上加；一加就 OOM 就说明该换更大的机器了。 64 slots ≈ 5.8 MB, 128 slots ≈ 11.6 MB. Start at 64; raise it when you see conn table full, and stop when raising it triggers the OOM killer.

TCP 窗口：tcp_rmem（比任何 zray 参数都重要）TCP window: tcp_rmem (matters more than any zray option)

128 MB 内存的路由器上，net.ipv4.tcp_rmem 默认上限约 930 KB，单条流的吞吐被「窗口 / RTT」卡住：190 ms 时约 1 MB/s。在这类机器上实测，把上限提到 4 MB 之后同一条链路的 HTTPS 吞吐从约 1 MB/s 变成 9–10 MB/s： On a 128 MB router the default net.ipv4.tcp_rmem ceiling is about 930 KB, capping one stream at roughly window / RTT — about 1 MB/s at 190 ms. On the reference box, raising the ceiling to 4 MB lifted HTTPS through the tunnel from ~1 MB/s to 9–10 MB/s:

sysctl 
echo 'net.ipv4.tcp_rmem = 4096 131072 4194304' > /etc/sysctl.d/99-zray.conf
sysctl -p /etc/sysctl.d/99-zray.conf

不要用 zray 的 sock_buf 来干这件事：它会关掉内核的窗口自动调优，还会被 net.core.rmem_max 截断。sock_buf 留 0。 Do not reach for zray's sock_buf here: it disables the kernel's window autotuning and is clamped by net.core.rmem_max. Leave sock_buf at 0.

从 v0.3 升级Upgrading from v0.3

0.5.0 在同一监听端口支持 SOCKS5 与 HTTP 代理，可通过 workers 配置网络工作线程，并提供可选的内核 AES-GCM 加密后端和动态 libc 链接构建。同时改进了 Vision 转发，并修复 TLS 密钥更新、连接关闭和旧内核随机数获取等兼容性问题。升级只需要换二进制： 0.5.0 supports SOCKS5 and HTTP proxy traffic on the same listener, configurable network workers via workers, optional kernel AES-GCM backends and dynamic libc builds. It also improves Vision forwarding and fixes TLS key updates, connection shutdown and random-number generation on older kernels. Upgrading is a binary swap:

OpenWrt 
/etc/init.d/zray stop
# 覆盖 /mnt/zray/zray，保留原配置 / overwrite the binary, keep the config
/etc/init.d/zray start

配置向后兼容：只写了顶层 server / uuid 的旧配置照常工作，connect_timeout_s 默认 5 秒。要留意的是： Configs stay backward compatible: a top-level server / uuid config keeps working, connect_timeout_s defaults to 5 s. Two things to keep in mind:

  • 开始用链式时，max_connections 要按连接数翻倍往上加（每条链占两个槽）。Once you start chaining, raise max_connections to twice the connection count (two slots per chained connection).
  • 0.4 之前没有 connect_timeout_s，入站侧的超时由 handshake_timeout_s 兜着；现在它只管入站，上游有独立的 5 秒硬超时。Before 0.4, handshake_timeout_s covered the upstream attempts too; now it is inbound-only and upstreams have their own 5 s deadline.
